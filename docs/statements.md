# The statements flavor: a base for search, not for checking

A snapshot of a promotion (docs/transplant.md, docs/consuming.md) holds every constant that a proof of a promoted theorem reaches, because the kernel checks the proofs again: 183,763 constants and 1.6 GB of `.olean` for 4,778 theorems. A **statements** export keeps each theorem as an **axiom of its type** and does not visit its proof, so everything only the proofs used drops out with them.

## Why this is sound for search (invariant I1)

`exact`, `apply`, `rw`, `simp [lemma]` and the elaboration of a statement use the *type* of a lemma. The proof of a lemma is never unfolded (proof irrelevance), so a lemma that stands as an axiom of its type serves the search. A proof found there is **checked afterwards in an environment that holds the real proofs** (the full snapshot, or Tengoku's own tree): untrusted search, trusted checking.

What it is not: a verified environment. `#print axioms` of a promoted theorem prints the theorem itself. A statements snapshot has to say so in its manifest (`flavor: statements`) and name the Tengoku commit its statements come from, whose independent check is what vouches for the proofs.

## What was built

* `tools/export/lean4export-statements.patch`: `lean4export --statements`, a theorem is written as an `axiom` line (same name, level parameters and type; `isUnsafe` false) and its proof is not visited, **except** a theorem that the value of a definition or an opaque constant mentions, which keeps its proof (the rule below). The exporter prints on stderr how many theorems that is. Nothing else changes.
* The same patch has two more options, both **off by default**: without them the output is byte for byte what the previous version of the patch wrote (checked on `Init`: the whole of it, a names file, root names, and a full closure without `--statements`; only the source line numbers in a PANIC line on stderr moved by two). `--drop-proofs` keeps **no** theorem with its proof (the first version of `--statements`: a definition that only computes through a proof is then refused by the kernel at replay, and `tengai-replay --stub-refused` turns it into an axiom of its type); `--own=MODULE_PREFIX` (repeatable; a module prefix, not a namespace: `Init.Data.Nat`) writes only the constants declared in the modules under the prefix and what they need, a *wave* of an export too large for one process, and which theorems are kept is decided over the whole environment, so every wave agrees. `compare_exports.py` against the full export passes on `Init` for the default (47,132 declarations, 1,028,389 terms, 2,533 kept), for `--drop-proofs` (46,473 declarations, 830,373 terms, none kept) and for two waves (`--own=Init.Data.Nat`: 3,438 declarations; `--own=Init.Data.List`: 5,729). On Tengoku the options have not been run yet.
* `tools/export/compare_exports.py`: two exports of one environment (full, `--statements`) agree on every declaration they share, without trusting the numbering of terms (each declaration is reduced to a digest with every name, level and term resolved): a theorem is an axiom with the same name, level parameters and type; the statements export has no theorem and nothing the full one lacks. 12 tests on synthetic exports; the workflow `export-statements` runs it on `Init` exported both ways before anything else.
* `.github/workflows/export-statements.yml`: the gates, then the wide sample of the transplant runs exported as statements (the same 4,800 roots as the 1.6 GB snapshot: a size to set against it), then the whole tree exported as statements (lines, bytes, time, memory) and, as a probe, each replayed through the kernel by `tengai-replay` (size of the module, what a session loads).
* **The whole tree** (`sample_mode=tree`, `seed_depth`, `drop_proofs`; tenro#104): `tools/promote/Modules.lean --prefix` lists every theorem of the tree by module, `tools/promote/tree_topics.py` makes the topics (`Seed/<area>`, `Intake/<library>`; an internal theorem, a name with a component that starts with `_`, is no root: the export of a whole tree does not write it, and `layers.py` refuses a topic theorem that is not in the export), the export takes `--drop-proofs` (the patch's version 2.4). `layers.py` also writes `<layer>.constants.jsonl`, every constant of a layer (the constructors and recursors of an inductive block too).
* **Libraries left out** (`exclude_libraries`, with `sample_mode=tree` and `tree=false`): a release that cannot hold a library (the licence text is missing at the commit the tree pins) exports the roots of the other libraries instead of `Tengoku.All`. `tools/promote/tree_roots.py` reads the aggregate `Tengoku/All.lean` (the libraries are the modules it imports), builds the import graph between the libraries from the headers of their files (as Lean reads a header: comments, `prelude`, `import` in any of its forms; an `import` in a docstring or after the first command is no import) and leaves out, with the libraries asked for, every library that imports one of them, down the chain, because a constant a statement reaches is in the export. `Modules.lean`, `lean4export`, `tengai-typeinfo` and `tengai-extinfo` take the kept roots; the report `tree-roots.json` (kept in the export artifact) says what was left out and why, and the manifest of the snapshot pins `excluded_libraries` (the release notes print it). A name that is not a root of the aggregate is an error. The attribution (`attribution.py --filter`, at export time and again at replay time, so an export made without the filter is repaired) does not name a library that was left out (a root `Tengoku.LanaBelyi` is the registry library `lana-belyi`; two libraries with one name are an error): the first real run's attribution still listed all 228 libraries, and the 8 without a licence text would have blocked the release for content that is not in the snapshot. With nothing excluded the roots are `Tengoku.All`, the export and the manifest are the ones they always were. 18 tests on a toy tree (a chain, a docstring that mentions an import, the header forms, a header longer than the first read); seven mutations of the tool each fail one.
* **Extension entries** (`ext_rows`, `scoped_instances`): the export run reads `tengai-extinfo` in Tengoku's environment over every constant of the layers (it expands nothing, hence the constants files), `tools/promote/ext_partition.py` splits the rows by layer (a row no layer holds is an error), each layer is replayed with `--ext` and its own rows; `tools/promote/ext_compare.py` reads the same rows back with the same tool in the snapshot's environment and compares them per kind (same, differs, lost, extra), compares the scoped instances (`sinst` rows: the namespaces an instance is scoped in, Tengai v0.0.20 on) as a kind of their own, counts the instances that `--scoped-instances` registers another way than Tengoku has them as deviations, and reports **Lean core's own constants** (the replay does not add them) apart, never judged; the manifest records `checks.extensions` and `checks.ext_faithful`.
* **An independent kernel** (`nanoda`): the replayed layers are read back out of their `.olean` files, exported by a lean4export **without our patch**, and checked by nanoda_lib at the commit Tengoku's independent check pins, with every axiom admitted (a theorem stands as an axiom of its type, so it checks every other declaration), after a selftest and a control that must stop on a statement-axiom.
* **Licence texts** (`tools/release/licences.py`): for each (repository, commit) the licence and notice files at the root, byte for byte, in the archive under `legal/` (manifest `legal`, `pack.py --legal`); the release gate (`tools/release/notes.py`, docs/releasing.md) refuses a snapshot without them, with a library whose text is not the licence the registry records, with an independent check that did not say ok, or with extension entries that were not compared or differ.
* `tools/export/export_stats.py`: the lines of an export by kind, bytes, zstd size, and the wall time and peak memory of the export from `/usr/bin/time -v`.
* `tools/promote/stmt_closure.py` and the workflow `stmt-closure`: the same question answered from the export of a sample alone.

The same question for Lean core alone, from the exports themselves (workflow `export-statements`, run 44951869407, `Init` exported both ways): the full export is 6,483,244 lines and 347 MB (59,591 declarations, 6.13 M terms); with `--statements` 1,008,897 lines and 59 MB (46,473 declarations, 0.83 M terms), 15.6 % of the lines and 13.5 % of the terms.

**The exporter shares terms up to binder names and binder info.** `lean4export` writes a term once, with the binder names and annotations of the first alpha-equivalent term it met (Lean's `Expr.eqv` ignores both), so which names a declaration carries depends on what was visited before it, and leaving the proofs out changes that. The first comparison of the two `Init` exports, which treated names and info as part of a term, reported 3,215 changed declarations for that reason alone; `compare_exports.py` now compares terms up to them and counts the declarations that differ only so (`binder_names_only`). A replay restores the names and annotations of the source from Tengoku's environment (`bi` rows), so the replayed statements are the source's.

The rule costs size (the first version, theorems as axioms only, was 147 MB for the sample, which the kernel then refused at `Rat.instEncodable`): 1.6 times the module, and the exporter's memory is the limit of the approach on a 16 GB runner (12.5 GB for the intake; the whole `Tengoku.All` with this rule would not fit, hence waves: the seed first, the intake on top of it). The replay is near the same limit: 14.3 GB of the runner's 16, in 37 minutes.

**One module of all the intake is over the cap.** The cold-load cap `C_load` is 0.25 s (`perf-budget.toml`, lowered only) and the whole intake as one module costs 0.30 s over an empty session (run 44991509898; minimum to minimum, 0.2305 s to 0.5264 s: +0.296 s). The cost does not grow with the number of constants: 11 times the constants (55,316 to 612,257) and 15 times the bytes cost 44 times the import time (0.125 µs a constant for the sample, 0.49 µs for the intake), so the cap cannot be read off the sample, only measured on what a session loads. The remedy is the one the proofs flavor already uses: a foundation and one layer per library (`tools/promote/layers.py`, `tengai-replay --import` and `--only`), so that a session loads the foundation and its own topic. The next section is that, measured.

## What the first replay of the whole tree refused, and the rule it taught

The whole tree exported as statements (69,255,348 lines, 4.10 GB; workflow `export-statements`, run 44952755442) was refused by the kernel at `Rat.instEncodable`. A minimal export of that one constant, both ways (`statements-repro`, run 44957656258, `Tengoku.Seed.Data.Rat.Encodable`), reproduces it: the two exports agree on every declaration (the stub's type is the theorem's, up to binder names), the full export replays, the statements export is refused. Read from the exports themselves:

* the definition is `Equiv.mk toFun invFun _proof_3 _proof_4` with `toFun`, `invFun` matches over a subtype `{d // 0 < d ∧ n.natAbs.Coprime d}`; `_proof_1 a b c d` is the proof of the conjunction `0 < b ∧ Coprime ..`, an auxiliary theorem whose value is `And.intro ..`;
* the declared type of `_proof_3` is `∀ x, invFun (toFun x) = invFun (toFun x)` (the type of the `rfl` that proves it), while the field wants `invFun (toFun x) = x`: the kernel has to reduce `invFun (toFun x)` to `x`, and that means reducing `And.rec` on `_proof_1 ..`, which is a constructor application **only once the theorem is unfolded**. With `_proof_1` an axiom the reduction is stuck and the definition is refused (the kernel, as far as I remember its source, does not eta-expand a structure in `Prop`, so it cannot get past a stuck proof of a conjunction; the evidence here is the refusal and the exports, not a reading of the kernel).

A theorem stood as an axiom can be typed against, rewritten with and applied; it cannot be **computed through**. The rule that follows, in the patch (`lean4export --statements`, v2): **a theorem that the value of a definition or an opaque constant mentions is exported with its proof**, the rest as axioms. It is decided once over the environment (`Expr.getUsedConstants` of every value), without running the kernel, and it is a superset of what the kernel needs (auxiliary proofs of definitions, well-foundedness proofs, instance proofs). The proofs of the kept theorems are not scanned again: what they mention stays a stub, which is enough to type them.

## What it does not say, yet

* **Coverage.** The intake snapshot holds what the 311,773 intake statements reach. The seed's other lemma statements are not in it: the whole tree has 743,024 theorem roots in 263 topics, 281,692 of them in 34 seed areas. The whole tree **exports** (`--drop-proofs`, 15.7 min, 12.2 GB), **plans** (266 layers, a foundation of 72,056 of 1,135,319 constants) and a part of it replays (the foundation, both groups and three topics: the table parse fits a 16 GB runner at 15.4 GB, no session over the cap, the slowest +0.074 s), but it has not been replayed whole, packed or checked. Without the kept proofs a definition that only computes through a theorem is refused by the kernel and stands as an axiom of its type: 1 of 64,480 in the foundation (`Rat.instEncodable`), none in the five other layers replayed.
* **Faithfulness to Tengoku.** For the intake snapshot: 635,787 of 635,787 constants, no problem (section above): the hash and the size of the type, the hash of the value, 32 bits and without binder annotations, so an agreement is strong evidence and not a proof. For the whole tree it has not been run (a read in Tengoku's environment over 1.1 million names).
* **Statement ids.** `tengoku-isnad` reads theorems; a statements module has axioms, and at the last count (22 Nov) 37 % of the tree's rows had no id in their source. The retrieval indexes keyed by id are not built for this snapshot; the layers index (`indexes/layers.jsonl`: theorem name to the layer that holds it) is.
* **Replay.** A definition whose body needs the kernel to unfold a theorem (a reduction through a well-foundedness proof) does not replay with that theorem as an axiom: it fails loudly, or, with `--stub-refused`, stands as an axiom of its type and is listed. With the rule of v2 none of the 612,257 constants of the intake export was refused (run 44991509898: the probe printed "0 declarations were refused by the kernel"). The seed's other lemmas, the part of the whole tree that no intake statement reaches, have not been replayed.
* **Instances.** Global instances are registered global (active when a layer is imported, as the proofs snapshot does). **Scoped instances are carried since Tengai v0.0.20**, each in the namespaces it is scoped in (`sinst` rows, tengai#23): inactive until the namespace is opened, as in Tengoku. Before that **no scoped instance was carried at all**: `tengai-extinfo` read the instance extension's current state, which holds the global entries and those of the open namespaces and none is open when a module is imported, so the sentence that stood here (*no instance of the intake's closure is scoped in Tengoku, 0 of 16,073*) described the reader, not Tengoku; Mathlib's pointwise instances and every `scoped instance` of the intake libraries were missing from every snapshot before it. `--scoped-instances` (every global instance registered scoped to the namespace of its layer's module, invariant I4: a session opens what it wants active) stays an option for a library that wants everything inactive; the owner's decision on it does not concern the instances Tengoku itself scopes any more. How many scoped instances the tree has, and whether Lean accepts each at registration, is not measured yet: the first replay with the rows of the v0.0.20 reader (snapshot-4) says.
* **Lean core's own constants.** The replay does not add what Lean core holds, so it cannot carry what a library changed about it (`instSMulOfMul`, above): the comparison reports them apart.
* **Parse memory.** The eager table parse of the whole tree peaked at 15.4 GB on a 16 GB runner (trial 45021157759, about 260 bytes an expression): it fitted once and **killed the runner on the next attempt** (run 45029701702, Tengai v0.0.18: `exit code 143` six minutes into the parse and nothing after it, no artifact). Tengai v0.0.19 keeps terms as records and declarations as text: the same parse takes 2 min 16 s at 4.10 GB (trial 45031823225, above). What is memory-bound now is the export itself (12.2 GB at lean4export) and the hash pass in Tengoku's environment (13.2 GB, `tengai-typeinfo --hashes` over `Tengoku.All`), both of which fitted.
* **Publication.** Nothing has been published. `release-snapshot` has run only as a dry run (run 45023865472, on the intake snapshot of run 45018433715); its gates now also require the licence texts, so that snapshot, packed without them, cannot be released as it is (docs/releasing.md).
* **Proving.** Nothing here says a prover does as well in a statements environment; that is a hypothesis for a campaign.
